In order to summarize how this system should behave, we need the following tables of variables
1)	Allowable VLANS per email domain table. For each domain policy, there is an entry in this table with columns ‘email domain’ and ‘VLANS’. The ‘VLANS’ column consists of a list of VLANs for the email domain. E.g. in one row, you might have ‘email domain’=english.op.org, and ‘VLANS’= ‘10, 20’. This is interpreted to mean that a user with email domain english.op.org can connect to VLANs 10 and 20 and have full internet access without the need of the administrator to approve full internet access. 
2)	Allowable VLANS per user table. For each user in the system, there is an entry in this table with columns ‘user_id’, ‘Allowable VLANs’, and ‘Needing Approval VLANs’. E.g. in one row, you might have user_id=5 (corresponding to user with email joe.blogs@english.op.org), ‘Allowable VLANs’= ‘10, 30’ and ‘Needing Approval VLANs’ = ‘20, 40’. In this case, user joe.blogs@english.op.org has full access to the internet from VLANs 10 and 30 without the need for admin approval, but would need admin approval to gain full access from VLANs 20 and 40. So, the row for joe.blogs@english.op.org overrides the VLAN 20 setting for english.op.org in table 1.
3)	REDUNDANT – MOVED TO TABLE 10
4)	Adoptable VLANS per email domain table. For each domain policy, there is an entry in this table with columns ‘email domain’ and ‘VLANS’. The ‘VLANS’ column consists of a list of VLANs for the email domain. E.g. in one row, you might have ‘email domain’=english.op.org, and ‘VLANS’= ‘10, 20’. Analogous to the table 1 case, this would be interpreted to mean that a user with email domain english.op.org can adopt devices connected to VLANs 10 and 20 and have full internet access for them without the need of the administrator to approve the adoption.
5)	Adoptable VLANS per user table. For each user in the system, there is an entry in this table with columns ‘user_id’, ‘Allowable VLANs’, and ‘Needing Approval VLANs’. E.g. in one row, you might have user_id=5 (corresponding to user with email joe.blogs@english.op.org), ‘Adoptable VLANs’= ‘10, 30’ and ‘Needing Approval VLANs’ = ‘20, 40’. Analogous to the table 2 case, user joe.blogs@english.op.org would be able to adopt devices on VLANs 10 and 30 so that they had full internet access without the need of admin approval, but would need admin approval to adopt devices from VLANs 20 and 40 so that they had full internet access. So, the row for joe.blogs@english.op.org overrides the VLAN 20 setting for english.op.org in table 1.
6)	MAC address status table. For each MAC address that has been detected by the network, there is an entry in this table with columns ‘MAC address’, ‘internet accessible’, ‘internet blocked’, ‘Assigned VLAN’, ‘device type’, ‘ownership_validated’, and ‘first seen date/time’. The MAC addresses in this table should be unique. ‘internet accessible’ can be true, false, or null. A value of null means a decision hasn’t been made and so the kea hook should add a block and put a dns hijack in place before giving out ips to a MAC address in which ‘internet accessible’ is null.  When ‘internet accessible’ is true and the VLAN the device is connected to is the same as the ‘Assigned VLAN’, then this means there are no blocks or dns hijacks on the ip for the MAC. ‘internet accessible’ must not be set to true until all such blocks/hijacks have been removed so that the value of this variable can be polled to check whether the device has full internet access. The value of ‘internet accessible’ being false should only be possible when the ‘Assigned VLAN’ is different from the current VLAN the device is connected to or ‘ownership_validated’ is not true. So for instance, if a user tries to connect to VLAN 20, and the admin instead assigns the user to VLAN 10, by polling the value of ‘internet accessible’ to see if it is false, the user’s captive portal can display a message informing the user that they are on the wrong VLAN and should connect to the VLAN specified by ‘Assigned VLAN’. When the user connects to the correct VLAN as specified by ‘Assigned VLAN’, the kea would check the ownership_validated (if it is a VLAN requiring a password as specified in table 10) to determined whether the ip it is giving out should be hijacked or not. More details below.  
7)	IP status table. This is a table containing the columns ‘IP address’, VLAN_ID, ‘lease start’, ‘MAC address’, ‘lease expiry’, ‘from blocked pool’, ‘DNS hijacked’
8)	Users table: Each row has user id, user email, first name, second name, password, telephone number, registration date submission, and expiry date. User emails are unique, so if a new submission arrives with the same email address and different first and second names or telephone number, these are updated, but the registration date submission stays the same. 
9)	MAC address users: This is a table that contains the columns ‘MAC address’, ‘User id’, ‘start date/time’, ‘end date/time’. This table is interpreted to mean that between start date/time and end/date time, user with user id owns the device with MAC address. This table is needed in the event of someone adopting a MAC address and then changing their mind or giving/selling/loaning their device to another person on the network. 
10)	VLAN config table: This is a table containing the columns ‘name’, ‘VLAN id’, ‘SSID’, ‘Wired allowed’, ‘Password required’, ‘subnet size’, ‘ISP router’
11)	ISP routers: This is a table containing the columns ‘name’, ‘subnet’, VLAN ID, ‘HP5130 port’ ‘DHCP snoop Trust’, and ‘Gateway ip’.
12)	RADIUS table: this is a table of MAC address/VLAN pairs that is consulted by the RADIUS server when the HP5130 assigns VLANs to devices connected over the ethernet. Each MAC address can only appear once in this table.
The dashboard displays the following sections:
A)	Unregistered devices: This lists all the entries in table 6 where either the MAC address doesn’t appear in table 9, or if it does, the ‘end date/time’ is not null for every occurrence of this MAC address in table 9. It also displays when the ‘first seen date/time’ for the device. The list of unregistered devices does a join on the ‘MAC address’ of table 7 with the most recent ‘lease start’ so that this section can also display the most recently assigned ip address for the MAC address and when its lease started and when it will expire. On each row, there is an assign button. The admin can click on this, and it brings up a dialogue in which the admin can assign it to a user and VLAN. This results in the MAC address being added to table 9 with the user_id set to the corresponding user in the dialogue and with the start date/time set to the current date/time and with the ‘end date/time’ set to null. It also results in ‘ownership_validated’ being set to true for the MAC address in table 6. Also,
a.	If the device is connected over the wifi, the VLAN drop down on the assign dialogue page defaults to the VLAN corresponding to the wifi, but the admin can select any other VLAN (apart from VLAN 250). It is not possible not to select a VLAN. Once the ‘Assign device’ is clicked, then:
i.	If the selected VLAN is different from the VLAN the device is connected to, the ‘internet accessible’ field is set to false on the row for the device’s MAC address and the ‘Assigned VLAN’ is set to the selected VLAN for the MAC address in table 6. Since there should already be a hijack/block in place for the device’s ip if the device is currently connected to the network, no hijacking/blocking updates are required.
ii.	If the selected VLAN is the same as the VLAN the device is connected to, the ‘Assigned VLAN’ field is set to the selected VLAN for the MAC address in table 6. If the entry in table 7 for the MAC address has a ‘lease expiry’ that hasn’t yet expired and the ‘from blocked pool’ for that entry is set to false, then the captive portal removes the DNS hijack rule from the IP tables of the pi for that ip, and the captive portal calls a script that updates the HP5130 which the ISP router is plugged into for that VLAN (as specified in table 11) which results in the ACL block rules for that ip being removed from the VLAN the device is connected to. This will result in the device having full internet access should it be connected to the network. Only once the DNS hijack rule and the HP5130 rules have been removed, the ‘internet accessible’ field is set to true for the MAC address in table 6 and the ‘DNS hijacked’ of table 7 is set to false. Note this last step should take place synchronously rather than asynchronously so that we can be sure that when the ‘internet accessible’ field is set to true, the blocks really have been removed. An email is then sent to the user with user id saying that the device with MAC and IP address specified has been assigned to them. This email should have a link by which the user can reject the assignation. In the unlikely event that  a blocked unregistered device is assigned to another user, the device will remain blocked on reassignment – so no change to the ‘internet blocked’ entry for the MAC in table 6.  
b.	If the device is connected over the ethernet, there is no default VLAN suggested, but the admin must select a VLAN (VLAN 250 is not an option) from the VLANs in table 10 for which ‘Wired allowed’ is set to true.    The ‘Assigned VLAN’ field is set to the selected VLAN for the MAC address in table 6 and table 12 is updated so that MAC if not present is added, and if it is present, the VLAN is set to the ‘Assigned VLAN’. The hp5130-replug.sh script is queued for the port the device is plugged into. There is also a relatively short lease time in case the wired device doesn’t reconnect to the ethernet and issue a DHCPDISCOVER request. No dns hijack/block updates are needed since VLAN 250 is always hijacked/blocked. 
B)	Users: this lists all the entries in table 8. Search filters should be available for this list of users, and it should be possible to change the search order/precedence by clicking on a column header. This list of users does a join on table 9 and table 6 so that it can show all MAC addresses owned by the user, their connectivity status, as well as the number of MAC addresses owned. It also does a join on table 7 finding the ip with the latest expiry for each MAC address owned by the user displaying the ip in brackets next to the corresponding MAC address. This list of users also displays the email and the full name of the user, and also the user’s registration date as well as an expiry date (if set).  It also does a join on tables 1, 2, 4 and 5 on the email domain and user so that the row can display VLANs which the user can connect to/adopt devices without admin approval. The display convention is that if a VLAN is allowed without admin approval in virtue of email domain in table 1, the VLAN is displayed in italics, if allowed via the user override in table 2, the VLAN is displayed in bold, but if the user override in table 2 states it is not approved automatically, the VLAN appears crossed out so you could have italics, bold, bold italics, crossed out, and crossed out italics. A similar scheme is used for displaying the VLANs for which a user can adopt devices that are connected to it as determined by tables 4 and 5. Next to each user, there is an ‘edit’ button in which the admin can change the first name, second name, telephone number, password, and the table 2 and table 5 overrides. Next to each user, there is also a ‘block’ or ‘unblock’ button.  
a.	If the block button is clicked, this goes through all the entries in table 9 where the user_id is set to the user and where end date/time is set to null. If there is no end date/time, then it is assumed the device has no future time limit on which the device is owned. For the corresponding MAC addresses which have ips in table 7 (that is, an ip for that MAC which hasn’t yet expired), the ‘internet accessible’ field for the MAC address is set to ‘null’, and the ‘internet Blocked’ is set to true. Also, for those ips in table 7 corresponding to the user’s MAC addresses that haven’t expired, the pi iptables are updated to apply the dns hijacker to these ips, ‘DNS hijacked’ is set to true,   and a script updates the HP5130 which the ISP router is connected to for the corresponding VLAN (as specified in table 11) to place an ACL block on the VLANs which these ips belong to. 
b.	If the unblock button is clicked, this goes through all the entries in table 9 where the user_id is set to the user and where end date/time is set to null and for each corresponding MAC address in table 6, the ‘internet blocked’ field is set to ‘null’. For those ips in table 7 for MAC addresses owned by the user that haven’t expired, and for which the device is on the same VLAN as specified in ‘Assigned VLAN’ (and for which ‘ownership_validated’ is set to true for VLANs in which ‘password required’ is set to true in table 10), the dns hijack and HP5130 ACL blocks are removed if present  (they won’t be present if the lease for the device was renewed after the block was put on the device, since after the lease renewal of a blocked device, kea will give it an ip in the blocked pool of the VLAN and delete the block/hijack on the ip the device previously had – in this case the unblocked user must either wait for their lease to renew or must disconnect and reconnect to the wifi to gain an ip in the non-blocked pool, so when a device is in the blocked pool, the captive portal website should poll ‘internet blocked’ and if ‘internet blocked’ is false, a message should be displayed saying ‘your device has been unblocked – to gain full internet access please disconnect your device from the wifi and reconnect to the wifi SSID corresponding to ‘Assigned VLAN’), and once the block/dns hijacks are removed, the ‘internet accessible’ field is set to true in table 6.  If the hijacker/blocks for the ips corresponding to the user’s MACs should remain in place due to the device being on a different VLAN from the ‘Assigned VLAN’ (or because ‘ownership_validated’ is not set to true on a VLAN for which ‘password required’ is set to true in table 10), then the ‘internet accessible’ field is set to false for that MAC address in table 6. If the device is connected over the ethernet, then a hp5130-replug.sh script is queued for the port the unblocked device is plugged into, and a message on the captive portal should appear (because there is a poll checking whether ‘internet blocked is false’) telling the user to pull the ethernet socket out of their device and plug it back in to get full internet access.
C)	Registered devices: this lists all the entries in table 9. Those entries for which end time/date is not null should appear greyed out to indicate they are not currently assigned to that user. Search filters should be available for this table, and it should be possible to change the search order/precedence by clicking on a column header. This display list does a join on the ‘MAC address’ of table 7 where the most recent ‘lease start’ and ‘lease expiry’ is within the start time/date and end time/date (if set – end time/date not set is taken to mean the end time/date is infinitely far in the future) of table 9 so that the registration section can also display the most recently assigned ip address for the MAC address/user combination and when its lease started and will end. This display list also does a join on table 6 so that the ‘device type’, ‘first seen date/time’ and connectivity status can be displayed. Next to each device of table 9 in which ‘end date/time’ is set to null, there is a ‘block’ or ‘unblock’ button as well as a ‘Reassign’ button and an ‘unregister’ button. 
a.	If the ‘Reassign’ button is clicked, this results in the entry in table 9 for the previous user/MAC address having its ‘end date/time’ filled in. A new row must be added to table 9 with that MAC address, the user id set to the newly assigned user, and the start date/time’ set to the current date/time, but the ‘end date/time’ should be left null. There should therefore be an AJAX update to the registered devices list when a different user is assigned to a device such that the new entry in the registered devices list is inserted so that it appears in the same location as the old entry (which should now be on the line below it). Also, if there is an ip in table 7 corresponding to the MAC address that hasn’t expired, the pi iptables are updated to apply the dns hijacker to this ip, ‘DNS hijacked’ is set to true in table 7, and a script updates the primary HP5130 to place an ACL block on the VLANs to which this ip belongs. 
c.	If the unblock button is clicked, the ‘internet blocked’ field in table 6 is set to ‘null’. A similar unblock process to B)  b. is applied – i.e. for the corresponding ip for the just unblocked MAC in table 7 that hasn’t expired (and the ip isn’t in the blocked pool), and for which the device is on the same VLAN as specified in ‘Assigned VLAN’ (and for which ‘ownership_validated’ is set to true for VLANs in which ‘password required’ is set to true in table 10), the dns hijack and HP5130 ACL block are removed, and once this is done, the ‘internet accessible’ field is set to true in table 6. If the hijacker/blocks for the ip corresponding to the unblocked MAC address is to remained blocked due to it being on a different VLAN from the ‘Assigned VLAN’ (or because ‘ownership_validated’ is not set to true on a VLAN for which ‘password required’ is set to true in table 10), then the ‘internet accessible’ field is set to false for that MAC address in table 6. If the device is connected over the ethernet, then a hp5130-replug.sh script is queued for the port the unblocked device is plugged into.
d.	If the ‘unregister’ button is clicked, 
i.	If ‘internet accessible’ was set to true and there is a non-expired lease in table 7 for that MAC, a dns hijack and ACL block on the HP5130 in which the ISP router for the VLAN it is connected to as specified in table 11 is put in place. (If ‘internet accessible’ is not true, and if all the leases in table 7 for the MAC have expired, then the device is not connected to the network, so there is no ip to block, but if there is a lease in table 7 that hasn’t expired for this MAC, then a block should already be in place, so again no block needs to be added)
ii.	The MAC in table 6 has ‘internet accessible’,  ‘Assigned VLAN’, ‘device type’, and ‘ownership_validated’ set to null. Any entry for that MAC in table 12 should be deleted. Table 9 is also updated so that the entry which had the MAC/user id combination has its ‘end date/time’ set to the current date/time.
iii.	The device should be removed from the registered devices and added to the unregistered devices – e.g. via AJAX, not a full-page refresh.
Now consider the following scenarios/actions:
1)	The user connects a device to a VLAN over the wifi. This will result in the device broadcasting a DHCPDISCOVER request over the VLAN. Kea will receive this request. The Kea hook looks in table 6 to see if the MAC address is already present.
a.	If the MAC address is not present in table 6, the kea hook adds a row for this MAC address in table 6 and sets the first seen date/time to the current time, but all other fields are set to null. Based on which VLAN kea receives the DHCPDISCOVER request, the kea hook will pick a free ip from the main pool for that VLAN. If no ips are available in the main pool, an email is sent to the admin with the importance flag set to urgent telling the admin to increase the subnet prefix. Assuming that ips are available in the main pool, Kea then issues a DHCPOFFER for that ip and waits for the corresponding DHCPREQUEST for that ip. Assuming it receives such a request, it then updates table 7 with the ip address, VLAN_ID, lease start, MAC address and lease expiry, and sets ‘from blocked pool’ to false and sets ‘DNS hijacked’ to true. The Kea hook then calls the script that updates the pi’s ip tables to hijack dns requests from that ip so that they are diverted to the dns hijacker. The Kea hook then asynchronously calls the script that updates the ACLs on the HP5130 which has the ISP connection for that VLAN (as specified by the HP5130 port in table 11) so that the new ip is blocked on this VLAN from accessing the internet. The Kea hook then issues a DHCP ACK confirming the lease. The captive portal should now appear on the device if it has a GUI.
b.	If the MAC address is present in table 6
i.	If ‘internet blocked’ is set to true, the kea hook looks in table 7 to see if an ip has been issued for that MAC address in the blocked pool which has yet to expire. 
1.	If there is a lease in the blocked pool that has not expired, kea issues a DHCPOFFER for the lease in the blocked pool, and on receiving the DHCPREQUEST for that ip, the kea hook updates the entry for that ip/MAC address/start time in table 7 with a new expiry and issues a DHCP ACK confirming the lease.
2.	If all the leases in the blocked pool in table 7 for the MAC address have expired,
a)	If a non-expired lease is found for the MAC, but not in the blocked pool, kea sets the expiry for this lease in table 7 so that it now has expired. (Note that there is a background routine running that checks table 7 about every 20 seconds for expired leases in which ‘dns hijack’ is set to true and sets ‘dns hijack’ to false and removes any hijack and ACL for that ip so that the ips are available for other devices.) 
b)	Either way, the kea hook checks table 7 to see whether the most recent ip it has issued for that MAC address from the blocked pool is still available. If so, kea issues that ip via a DHCPOFFER, or if not available, kea issues another ip in the blocked pool via a DHCPOFFER. (If no ips in the blocked pool are available, an urgent message is sent to the admin saying that no ips are available in the blocked pool for that VLAN) Then on receiving the corresponding DHCPREQUEST, the kea hook adds a new entry to table 7 with the lease start set to the current time, the lease expiry set to the  start time + default lease time for the blocked pool, the VLAN set to the VLAN the device has connected to, and the ‘from blocked pool’ set to true, and then kea issues a DHCP ACK confirming the lease.
ii.	If ‘internet blocked’ is not set to true.
1.	If there is a lease in the non-blocked pool for the MAC address in table 7 that has not expired, kea issues a DHCPOFFER for the lease in the non-blocked pool, and on receiving the DHCPREQUREST for that ip, the kea hook updates the entry for that ip/MAC address/start time in table 7 with a new expiry and issues a DHCP ACK confirming the lease. Since the lease has not expired, whatever dns hijack or ACL block that were present or absent should still be correct for the MAC’s ip address.
2.	If all the leases in the non-blocked pool for the MAC address in table 7 have expired,
a)	If a non-expired lease is found for the MAC in table 7, but in the blocked pool, the kea hook sets the expiry for this lease in table 7 so that it now has expired. 
b)	Either way, the kea hook checks table 7 to see whether the most recent ip kea has issued for which ‘from blocked pool’ is set to false is available. If it is available, kea issues that ip via a DHCPOFFER or if not available, kea issues another ip that is free and in the non-blocked pool via a DHCPOFFER. If there are no free ips available for that VLAN in the non-blocked pool, the kea hook sends a message flagged as urgent/important to the admin saying that the pool for that VLAN is full and that the prefix for that VLAN subnet needs to be updated.  On receiving the corresponding DHCPREQUEST, the kea hook adds a new entry to table 7 with that ip and MAC address with the lease start set to the current time and the expiry set to the default, and the VLAN set to the VLAN the device has connected to.
i)	If the ‘Assigned VLAN’ is null, then ‘internet accessible’ is set to null. (Note that it should be impossible for ‘Assigned VLAN’ to be non-null and for there to be no user assigned to the MAC in table 9. For ‘Assigned VLAN’ can only be set when there is a user for that MAC specified in table 9 with ‘end time/date’ set to null. For if a user rejects ownership of a device, the act of rejection not only unassigns a user for the MAC by setting the ‘end date/time’ in table 9 to the current date/time, but also sets the ‘Assigned VLAN’ to null.)
ii)	If the ‘Assigned VLAN’ is not null and is different from the VLAN the device is connected to, ‘internet accessible’ for the MAC in table 6 is set to false.
iii)	If the ‘Assigned VLAN’ is the same as the VLAN the device is connected to but ‘ownership_validated’ is not true and table 10 has ‘Passwrod required’ set to true for that VLAN, ‘internet accessible’ for the MAC in table 6 is set to null.
iv)	Once the ‘internet accessible’ status has been set, kea issues a DHCP ACK confirming the lease.
v)	If ‘internet accessible’ for the MAC in table 6 is not true, a dns hijack is put on the ip via an update of the pi’s iptables, and for the new ip/MAC address entry in table 7, the ‘DNS hijacked’ entry is set to true.  Also, for the HP5130 which is connected to the ISP router for the VLAN the device is connected to as specified in table 11, an ACL block is put in place for the MAC’s ip address kea has just given it.
2)	The user’s device is already connected to a VLAN over the wifi and has a DHCP lease, but wishes to renew it. The MAC address should therefore exist in table 6. The device will issue a DHCPREQUEST with the ip it already has. The behaviour should be much the same as the DHCPREQUESTs issued just after a DHCPOFFER. However, it is possible that the ‘internet blocked’ status for the MAC address in table 6 has changed since kea first made the DHCPOFFER. Therefore,  if the ip specified in DHCPREQUEST  is within the non-blocked pool but the ‘internet blocked’ for the MAC in table 6 is set to true, or if this ip specified in the DHCPREQUEST is within the blocked pool, but the ‘internet blocked’ for the MAC in table 6 is not set to true, the corresponding line for the current MAC/IP address in table 7 for the present lease should have its expiry updated to be expired by the kea hook, and kea should issue a DHCP NAK. This should result in the device issuing a new DHCPDISCOVER which will be handled as described above in 1).
3)	A user connects a device to the network with an ethernet cable. 
a.	If the RADIUS server database has the device’s MAC address/VLAN, the HP5130 puts the device on that VLAN. The DHCPDISCOVER and DHCPREQUEST handling is now identical to the description in 1) and 2) above. 
4)	A user’s device opens the captive portal root page. Let’s suppose this is http://bf-network.duckdns.org.
a.	If the captive portal is unable to find the MAC address of the device via the get_client_mac function, this presumably means the device is not on the local network. In which case, the root page should redirect to an https login page https://bf-network.duckdns.org/login which asks for an email and a password. Once the password is entered and agrees with the password in table 8, a captcha should be completed before the credentials are submitted. If the password is incorrect but the user email and the password exist in table 8, an opportunity is presented to resubmit the password again and a ‘forgot password’ link is also presented. Clickin on the ‘forgot password’ link results in an email being sent to the user’s email. Assuming the password has now been entered correctly,  if MFA hasn’t been set up, the user should set this up, but if MFA has been set up, the user should be asked for the MFA code from their app. Once logged in, the user is then redirected to their home page https://bf-network.duckdns.org/user_home. 
b.	If the captive portal is able to find the MAC address of the device via the get_client_mac function, this presumably means the device is on the local network and so this MAC address should exist in table 6. There is a polling function that checks the ‘internet accessible’, ‘internet blocked’, and ‘Assigned VLAN’ for the MAC address in table 6 and also check whether the MAC address appears in table 9 with ‘end date/time’ set to null.
i.	If there is no entry in table 9 in which the MAC address appears with ‘end date/time’ null, this means that the device is not currently registered, and so http://bf-network.duckdns.org  should display the registration form on which the user can enter their first name, second name, email, device type and user agreement, and if connected over the ethernet, there should be a drop down of VLANs for which ‘wired allowed’ is true in table 10. By the selected VLAN, we mean either the VLAN the user’s devices is connected to if over the wifi, or the selected VLAN if connected to the network over the ethernet. On submission:
1.	 If the user email is not in table 8, the captive portal adds a row with the user email, first and second name, phone number, and registration submission date.
2.	If the user email is in table 8, the captive portal just updates the first and second name on phone number corresponding to the user email.
3.	The ‘device type’ for the MAC address in table 6 is set to the value submitted in the registration form. 
4.	If there is a user entry for this user in table 5 which in which the ‘Needing Approval VLANs’ contains the selected VLAN, or if the user domain entry for this user is in table 4 and the VLANs list in that row does not contain the selected VLAN, or if the user domain entry for this user is not in table 4, then an email is sent to the admin saying this user with the MAC address and the IP it has would like internet access from the selected VLAN, and there should be a link to  review and approve the request.  The page this links to give the admin the opportunity to accept the selected VLAN, and in doing so sets ‘Assigned VLAN’ to the selected VLAN, or the admin might decide to set the ‘Assigned VLAN’ a different VLAN, or not to set it to any VLAN, and instead sets ‘internet accessible’ to false. The admin can also specify a reason for the decision they’ve made when submitting it. 
5.	If the conditions of 5. do not hold, ‘Assigned VLAN’ in table 6 for the MAC address is set to the selected  VLAN.
6.	An entry is then added to table 9 in which the ‘MAC address’ field is set to the device’s MAC address, the ‘user id’ field is set to the user id corresponding to the registered email address in table 8, the ‘start date/time’ field is set to the current time, and the ‘end date/time’ field is set to null.
ii.	If there is an entry in table 9 in which the MAC address appears with ‘end date/time’ null, this means that the device has been registered, though it may or may not have full internet access.
1.	If the selected VLAN has ‘password required’ set to true in table 10 and ‘ownership_validated’ is set to false for the MAC in table 6,

Here is an account of how to register on one site and allow automatic registration on another site: 
•	Suppose my organization has three premises, A, B, and C. The user connects to premise A and registers there. This results in the registration details being forwarded to the central server. This message should be queued so that if the central server is down, it will try to send the message again. It will stop trying once it has received a registration response from the central server. The user then goes to premise B, connects to the same wifi network. The local network doesn't recognize the device so consults the central server and finds the registration there so updates the local network at premise B with the registration details and also updates the central server to say that these registration details are now on premises A and B. The admin then blocks this device on site A. This results in the usual ACLs on the HP5130s and hijacks on the premise A network. It also results in a message being queued to send to the central server with the block instruction (and will wait for a response to know the instruction has been carried out). The central server will then queue a message to the other local networks which have this device registered with it - so it will contact the network on premise B. It knows not to send the block instruction to A, because that's where the original instruction came from, and it knows not to send the block instruction to C because the network at that premises doesn't have the registration of the device there so there is nothing to block. When premise B receives the block instruction, it will check if the device has an active lease, and if so apply an ACL block on the HP5130s at B and put a hijack on B's pi. It will also set the internet blocked flag to true. A message should then be sent to the central server to say the block is in place. If there isn't an active lease at B, the internet blocked flag will mean that if the user should try to connect this device, then it will be placed in the blocked pool. Regarding premise C, if the user tries to connect there, it won't have the details, so it will consult the central server. Assuming there is no timeout, it will receive the registration details but also be told that the device is blocked. So the blocks and dns hijack that are intially in place for devices that first connect to the network won't be removed. Also the 'internet blocked' flag will be set on premises C so that the user is told that their device is blocked. On the other hand, if there is a timeout because the central server is down, a message is queue with the registration details and when the central server eventually receives the message it will see that the device has been blocked and will send a response to C saying the device needs to be blocked. Of course, now the central server database would also be updated to say this device is registered (and blocked) at premises A, B, and C. There would also need to be a corresponding process whereby a device could be unblocked. Also, the central database also needs to keep track of blocked users, and so these would need to be sychronized across the different premises in an analogous way to how the device registration details are synchronized across different premises. In the case when a device is deregistered either by a timeout on not accepting the registration by the user, or the user rejecting the registration, or the admin deleting a device, this should result in the entry for the device in the central_devices being deleted and this should fan out to any other sites so that the MAC entry (if it exists) in table 6 of these other sites has ‘internet accessible’,  ‘Assigned VLAN’, ‘device type’, and ‘ownership_validated’ set to null, and any entry for that MAC in table 12 on these sites should be deleted, and Table 9 on these sites is also updated so that the entry which had the MAC/user id combination has its ‘end date/time’ set to the current date/time.
